# commit と計画のタスクの接頭辞 [作品] / [仕組み] の定義 (2026-10-29)
出典: 本人の指摘 (2026-10-29 の会話)。「計画の中の [仕組み] は意味が違う。仕組みというのは開発の流れそのものであって、この作品に固有のものではない」。

## 経緯
- v0 で「基盤・テスト・hook・配置は `[仕組み]`、曲・振り付け・config の調整は `[作品]`」と定めた (docs/plan/v0-phase1.md、docs/plan/v0-phase2-core.md「commit の規律」)
- 目的は docs/system-design.md「作品が出ないのに仕組みの変更だけ増えたら refine_idea 型の兆候とみなす (git 履歴で見る)」を機械的に見ること
- その目的に照らすと、ゲームのコード (sim・描画・音・入力) は作品そのものであり、「仕組み」ではない。v0〜v2 の計画と commit はこれを取り違えていた

## 定義 (2026-10-29 から)
| 接頭辞 | 意味 | 例 |
|---|---|---|
| `[作品]` | このゲームに属するもの全部 | 曲、振り付け (assets/)、src/config.ts、src/ のゲームのコードとテスト、描画、音、入力、ゲームの文書 (docs/choreo-format.md、assets/choreo/README.md、docs/play-image.md)、版の計画 (docs/plan/v*-phase*.md) のゲーム側のタスク |
| `[仕組み]` | 作品を育てる開発の流れ。別のゲームを同じ流れで作るときにも持っていくもの | docs/NEXT.md、CLAUDE.md のセッション規律と承認の扱い、不満の受け口と分解の手順 (docs/decisions/v*-feedback.md の「仕組み側の学び」)、docs/system-design.md、docs/plan/loop-*.md、キュー・hook・起動スクリプト、acceptance.json のガード |

- 迷うとき: 「別のゲームを同じ流れで作るときにも持っていくか」。持っていくなら `[仕組み]`、このゲームにしか無いなら `[作品]`
- 1 つの commit に両方が混ざるなら分ける。分けられないなら主な方を付ける
- 計画文書のタスクの表記も同じ定義。v3 からはゲーム側のタスクに `[作品]`、流れ側に `[仕組み]`

## 過去の履歴の扱い
- 2026-10-29 より前の commit は、ゲームのコードを `[仕組み]` と付けている (例: `[仕組み] v2 T5: 相殺 (敵の当たりを消す) と uncancelable`)。過去の commit メッセージと計画文書は書き換えない
- refine_idea 型の兆候を git で見るときは、この日以降の履歴を新しい定義で読む。それ以前は src/ と assets/ への変更を `[作品]` とみなして読み替える
